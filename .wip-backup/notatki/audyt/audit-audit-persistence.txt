SUMMARY: All persistent state is one compact JSON document, matura.json, in the app's private files dir, owned by Repository (app/src/main/java/com/matura/app/data/Repository.kt). MainActivity builds one Repository per Activity instance (MainActivity.kt:17); MaturaApp (ui/App.kt) is the only consumer, holds an immutable SaveData snapshot in Compose state and re-reads it with refresh() after writes. SaveData (model/Models.kt:243) = schemaVersion, Profile, sesja (learn.StanSesji?), Options, sets (a full copy of the 102-set catalog plus own sets), scores, progress (Map keyed entryId + U+001F + direction -> WordProgress). Serialization is kotlinx-serialization-json 1.7.3 with ignoreUnknownKeys and encodeDefaults; the file is about 154 KB, nearly all of it the catalog copy. load() reads main, then .bak, then defaults (an unparseable main is renamed to .uszkodzony), injects BuiltInSets.all() only if no built-in set exists, runs migrate() (schema 0 to 3: stamp, entry ids, catalog refresh with progress carry-over) and caches the result; it never writes. save() encodes the whole document, writes .tmp with fsync, rotates main to .bak, renames .tmp to main, and updates the cache only on success; lastSaveError drives a banner. Writers are the update{} helpers (upsertSet with EntryId.reconcile, deleteSet, setOptions, setProfile, recordGame), setSesja, and recordAttempt (Srs.applyTo plus an optional daily-session trace in one write, skipped when only bookkeeping fields change). Entry identity comes from learn/EntryId ('w' + SHA-256 prefix of catalog content, frozen through data/entry-ids.json aliases; 'u' + random for own rows). All I/O is synchronous on the UI thread. The data, model and learn sources equal the shipped 0.9.18 tree except punctuation in comments, so the on-disk format is the production format and the merge itself needs no migration.

INTEGRATION: Nothing was built or run (read-only); test names below are what pins each behaviour.

1. ATOMIC SAVE (Repository.writeAtomically, Repository.kt:466-490). Order: write matura.json.tmp + fd.sync() (474) -> file.renameTo(backup) (477) -> tmp.renameTo(file) (480, IOException on failure) -> finally delete tmp (488). A failure before 477 (disk full) leaves main and .bak untouched. Between 477 and 480 matura.json does not exist: a kill there leaves .bak = previous state and a complete .tmp = newest state; readBestAvailable (418-434) never looks at .tmp and the next save truncates it, so one save is lost. No directory fsync. Optional hardening: if main is missing and .tmp parses, use it.

2. BACKUP / QUARANTINE. .bak is rotated on every successful save, and StartScreen saves on every launch (App.kt:127), so .bak is at most one save behind. read() (437-445) treats any Exception, including a transient IOException, as corruption; main is then renamed to the single slot matura.json.uszkodzony (451-459), which a later quarantine overwrites. Falling back to .bak or to defaults is only logged: the student is not told, and in a release build the quarantined file is unreachable without root. After a fall-back to defaults, an unreadable .bak is overwritten by the second save.

3. CACHE. cache (62) is set in load() (88) and after a successful write (109) only, so a failed save also drops the change from memory. Pinned by PersistenceTest 'nieudany zapis nie udaje sukcesu' and PostepIntegracjaTest 'nieudany zapis nie udaje, ze postep zostal utrwalony'. Callers must act on the Boolean; no App.kt call site does. lastSaveError (73-75) means 'the last save failed', is cleared by any later success (110) and is sampled only in App.refresh() (App.kt:79-82), which is skipped per attempt (App.kt:183-201): a failed attempt save followed by a successful one is never shown and never retried. App's snapshot is also stale after the three setSesja calls without refresh (App.kt:329, 333, 338).

4. MIGRATION. migrate() (248-254): below 2 nadajIdentyfikatoryWpisom (368-396), below 3 odswiezZestawyWbudowane (283-312) + przeniesPostep (327-344), then stamps SCHEMA_VERSION (518). Idempotent through the stamp; determinism (needed because load() does not persist the result) is pinned by MigracjaTest 'drugie uruchomienie niczego nie zmienia'. A schemaVersion above the current one is returned unchanged (249). I re-derived every catalog id from content with a script: 2084 entries, 2018 distinct ids, 0 mismatches against the EntryId.builtIn rule and data/entry-ids.json. The 0.9.4 fixture differs from today's catalog in exactly four entries (v026[0], v031[14], v035[15], v062[13]), all covered by EntryId.ALIASY (EntryId.kt:78-87). Set ids v000..v101 are unchanged since the first Matura commit and BuiltInSets.kt has not changed since before schema 3, so no shipped save is missing a set or a correction today. Master 0.9.0 files are ordinary schema-0 files.

5. BOOKKEEPING. recordAttempt (162-178) throws IllegalArgumentException from Srs.key (Srs.kt:138-144) for a blank entryId or Direction.RANDOM; the check at Repository.kt:202 is unreachable because applyTo (169) throws first. All four modes filter before calling (GameEngine.kt:534, MultipleChoiceScreen.kt:155, TrueFalseScreen.kt:124, TimeAttackScreen.kt:433); new callers must do the same. Because of skipped writes (176), lastTask/lastAttemptId are not always the last attempt (no reader today). recordGame (216-233): top 50 per mode with a stable sort, so a new score equal to the 50th is dropped; timesPlayed only for a set id present in sets ('mix-all' is not). Every finished round is recorded, including 9-life calm rounds from the daily session and hard-word practice, as CLASSIC under the title 'Losowanie ze wszystkich dzialow'. Achievement is not persisted (derived by unlockedBy), despite the KDoc at Models.kt:206.

6. THREADS. Every repo call is on the main thread (App.kt lambdas and LaunchedEffects; the RawMicTest thread does not touch it), so nothing races today. load/save/recordAttempt are @Synchronized, but update (119), setSesja (145) and all update-based writers read and write in two separate critical sections. If saving moves off the UI thread, make update and setSesja @Synchronized (the monitor is reentrant); otherwise one of two interleaved updates is lost while both return true. The write is also a per-answer UI-thread cost: the whole document (153,650 B with empty progress by the authors' own measurement, plus roughly 210 B per practised word-direction because encodeDefaults writes all eight WordProgress fields) is encoded and fsynced for every answer that changes state. I did not measure the resulting frame time.

7. DISK FULL. save() returns false, lastSaveError is set, cache/main/.bak are unchanged, .tmp is removed. The app keeps working but retains nothing; the banner (App.kt:399-406) appears at the next refresh(), for answers only at the end of the round.

8. NEW FIELDS (Json at 44-59; explicitNulls and coerceInputValues at defaults). Safe without a schema step: any new property WITH a default in SaveData, Profile, Options, WordSet, Entry, ScoreRecord, WordProgress, StanSesji (precedents: Options.systemKeyboard, ScoreRecord.mode, Entry.id, SaveData.sesja/progress). Not safe: a property without a default (also a nullable one without '= null'); renaming a property (the old key is silently ignored and the value resets; use @SerialName); renaming or removing an enum constant (Texture, Speed, UiLanguage, Direction, GameMode, TaskKind); making sesja or lastTask non-null (explicit nulls are on disk). Each of the last three makes every existing file unparseable: main is quarantined, the .bak of the same generation fails too, and the app silently starts from defaults. encodeDefaults also freezes today's defaults into each file, so a later change of a default does not reach existing users. StanSesji (Sesja.kt:115-141) is part of the save although its KDoc (111-113) says it is not; dzien is required. Code that rebuilds objects drops new fields: SetEditorScreen (Screens.kt:512-528), EntryId.reconcile (carries only id), odswiezZestawyWbudowane (replaces whole entry lists). There is no persisted 'session finished today' marker: onZakoncz stores null (App.kt:344), so re-entering the same day starts a new session; StanSesji.zakonczona exists and could carry it.

9. STEP 4. Must: bump SCHEMA_VERSION and add 'if (out.schemaVersion < 4)' after line 252, working on out; stay pure (no Random, no clock, no I/O); exist for ANY catalog change, because each save keeps its own catalog copy; append catalog sets the save lacks (odswiezZestawyWbudowane only maps over existing sets at 291, and load() injects the catalog only when there is no built-in set at all, 83-85); keep ids frozen by adding each new wording as an alias in both data/entry-ids.json and EntryId.ALIASY (EntryIdTest 'kazdy wpis katalogu ma identyfikator zgodny z trescia' enforces builtIn(content) == id; without the alias the word's progress is orphaned); preserve timesPlayed, createdAt, own sets, profile, options, scores, sesja; add a golden fixture of a real 0.9.18 file (schema 3 with progress, sesja and an edited built-in set), which does not exist. Must not: write from load(); delete built-in sets missing from the catalog; prune progress; reuse the wholesale refresh without a decision on student edits. The KDoc at 276-281 promises that edits made after the 0.9.18 update survive; a second refresh erases every row a student added or changed in a built-in set since then.

- [medium/data-loss/certain] editor-discards-set-on-failed-save: Set editor closes and throws away the typed set when the save fails
  app/src/main/java/com/matura/app/ui/App.kt:364
  DESC: onSave = { set -> repo.upsertSet(set); refresh(); pop() } ignores the Boolean returned by Repository.upsertSet. Repository.save (Repository.kt:107-115) updates the cache only after a successful write, so on failure refresh() reloads the old document and pop() destroys the editor, whose rows exist only in remember state (Screens.kt:423-430). The banner text (Strings.kt:93-95) says the last change 'may not survive closing the game', but the change is already gone from memory.
  SCEN: Phone storage is full. The student types a 25-row own set and taps ZAPISZ. Writing matura.json.tmp fails with ENOSPC, upsertSet returns false, the screen returns to ZESTAWY, the new set is not in the list and every typed row is lost. The banner suggests the change still exists until the app is closed. The same happens to edits of an existing set.
  FIX: Use the result: val ok = repo.upsertSet(set); refresh(); if (ok) pop(). Keep the editor open on failure so the student can free space and retry, and reword saveFailed to say the change was not saved.

- [medium/data-loss/unsure] per-activity-repository-cache: Each MainActivity instance has its own Repository cache; a second live instance overwrites newer data
  app/src/main/java/com/matura/app/MainActivity.kt:17
  DESC: Repository(applicationContext) is created per Activity instance, and load() returns that instance's private cache forever (Repository.kt:62, 79) without checking whether the file changed. This is correct only while at most one instance is alive per process. MainActivity is the exported, standard-launch-mode LAUNCHER activity with no isTaskRoot guard. On Android 7 to 9 (minSdk is 24) a first start from the Play or installer 'Open' button followed by a start from the launcher icon is the well-known case that stacks a second root activity on the first. I could not reproduce device behaviour here; the code-level consequence of two instances is certain.
  SCEN: Instance A (opened from Play) has cache D5. Home, then the launcher icon creates instance B on top of A; the student plays in B and the file advances to D20. WYJSCIE or back finishes B and reveals A, still showing D5. The next action in A (an answer, an option toggle) runs save(D5 + change): D20 moves to .bak and is destroyed by the save after that. All progress, scores and sets from session B are lost without any message.
  FIX: Make the Repository a process-wide singleton (companion-held instance keyed on filesDir, or an Application subclass), and optionally finish duplicate launcher instances in onCreate (if !isTaskRoot and the intent is MAIN/LAUNCHER, finish and return).
